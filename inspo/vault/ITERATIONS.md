# Iterations — how the bookmark pipeline actually got built

This is the running engineering log of the bookmark-ingestion project (2026-06-04 → ongoing): a system that turns X/Twitter bookmarks into a queryable design-inspiration knowledge base. It started as a hand-curated markdown file and became a launchd daemon that watches `~/Downloads`, diffs bookmark exports against a ledger, harvests real URLs out of Twitter's metadata blob, drives a headless Claude + Playwright enrichment pass that tears down each site (DOM-probed colors, fonts, tech stack, media descriptions), and renders everything into this Obsidian vault where 155 sites connect through four controlled facets. Nothing here went right the first time. This file documents every pathway — including the dead ends — as raw material for a future write-up.

## System at a glance (current)

- **Trigger:** launchd `WatchPaths` agent on `~/Downloads` → `run.sh`, serialized with a `mkdir` lock (macOS ships no `flock`).
- **Deterministic core:** `tools/ingest/ingest.py` diffs the newest `twitter-Bookmarks-*.json` against `inspo/_ledger.json` (332 tweet ids processed so far), deep-walks each record for URLs, and emits chunks of at most 5 items.
- **Judgment layer:** `claude -p` (Sonnet, via `NEOUD_ENRICH_MODEL`) with an isolated headless Playwright MCP — picks the primary URL, writes prose teardowns, probes the DOM for real tokens, views/describes attached media, and classifies each site against `tools/ingest/taxonomy.json`.
- **Deterministic writers:** merge into `inspiration.json` (256 items, 156 site teardowns — the source of truth), splice a managed region into `inspiration.md`, advance the ledger, archive the export, and rebuild this vault (`render_vault.py`).
- **The vault:** one note per site, connected by four facets — vertical (11 values), vibe (10), topic (18), mode (3). 40 tag nodes, 919 explainable site↔site edges. See `INDEX.md`.
- **Backed up:** private repo at github.com/neoudhaile/bookmark-ingestion (232 MB including full-page screenshots).

## Iteration 0 — Manual curation and the color-heavy teardown (2026-06-04)

**What we built.** X bookmarks manually exported to JSON, then hand-assembled into `inspiration.md` + `inspiration.json` with categories and tags. Alongside it, the idea of a per-site "design teardown": open the site in a browser and record how it's built. The first live teardown was [[weirdfolders.com]] via the Playwright MCP, using a heavily structured, color-token-centric schema — palette arrays, design tokens, a type scale.

**What broke.** The schema optimized for the wrong thing. Owner feedback, verbatim: "this schema is really color heavy… I want it to be about the website, what it does, how it's designed, in text." A teardown that's mostly hex codes tells you nothing about why a site is worth bookmarking.

**What replaced it.** The prose pivot below. Lesson zero of the project: the first schema you design will encode what's easy to extract, not what you actually want to know.

## Iteration 1 — The prose-forward schema (2026-06-04)

**What we built.** The teardown was redesigned around four prose fields — `what_it_is` / `what_it_shows` / `how_it_works` / `how_its_designed` — plus a one-line palette, a one-line fonts note, and a `pattern_keywords[]` array. Color got demoted from arrays of tokens to a single sentence.

**Why it stuck.** This is still the spine of every site note in the vault (see any note, e.g. [[mo1.app]]). Everything added later — DOM probes, tech stack, media — hangs off these four paragraphs rather than replacing them. It was an explicitly human decision point, and it shaped the whole system: the database is for *reading about* websites, with structured data in a supporting role.

## Iteration 2 — Automating ingestion: the daemon (design 2026-06-04)

**What we built.** With the schema settled, the manual loop needed closing. Brainstormed bookmark sources: the paid X API, logged-in scraping of x.com, a share-sheet webhook, or manual re-export auto-processed. Chose manual re-export — free, no API tier, and the user controls cadence.

The feasibility test on a real 154-item export produced the finding the whole architecture rests on: tweet text carries only `t.co` stubs, and the top-level `entities.urls` recovers real destinations for just **16/154** bookmarks. But a deep recursive walk of the export's full metadata blob — card unfurls, quoted tweets, author bios — recovers **127/154** (~82%). The remaining ~27 are genuinely link-free tweets. So: a deterministic script can harvest links, but choosing the *primary* site (a tweet linking both `12matcha.com` and the author's portfolio should file under [[12matcha.com]]), writing titles, and tagging still need a model. Hence the hybrid split.

Architecture: launchd `WatchPaths` on `~/Downloads` → deterministic Python ingest (diff by tweet id against a ledger; recursive URL harvest; utility-domain denylist so `linktr.ee`/`cal.com` never become the primary URL) → `claude -p` enrichment (title/category/tags/primary-URL judgment + Playwright teardowns) → deterministic writers (merge JSON, splice a managed region into the md so hand-written prose is never touched, ledger update, archive the raw export). Built via a 13-task TDD plan executed with subagent-driven development, 20+ unit tests, then validated live on a 33-bookmark delta before the daemon was ever armed. The daemon was deliberately built *last* — it's just a trigger, and a background job should not be automated until the pipeline it triggers is proven by hand.

## Iteration 3 — The daemon hardening saga: macOS fights back (June 2026)

The pipeline worked when run by hand. Making it work *unattended under launchd* took six distinct fixes, each of which is its own small war story:

1. **TCC.** launchd jobs get no Downloads/Documents access by default — the daemon died with "Operation not permitted" reading the very folder it watches.
2. **The killed bash.** Solution to #1: copy the interpreter to a dedicated path (`~/.local/bin/neoud-bash`) so TCC permissions can be granted to *it* specifically. Except macOS SIGKILLed the copy (exit 137): a copied `/bin/bash` executes its **arm64e** slice, an ABI reserved for platform binaries. Fix: `lipo`-thin the copy to x86_64 and ad-hoc codesign it — the daemon's shell now runs under Rosetta, on an Apple Silicon Mac, on purpose.
3. **The wrong `claude`.** The `claude` on PATH was a cmux terminal wrapper that fails headless. The daemon must point at the real binary (`~/.local/bin/claude`).
4. **The missing `npx`.** Playwright MCP wouldn't launch because `npx` lives inside nvm, which a daemon PATH knows nothing about. The plist now hardcodes the node bin dir (`~/.nvm/versions/node/v18.20.8/bin`).
5. **Profile locks.** The daemon's browser collided with interactive Claude sessions using the same profile. Fix: a dedicated MCP config running `--isolated --headless`, loaded with `--strict-mcp-config` so nothing else leaks in.
6. **Permissions.** `--dangerously-skip-permissions` for unattended tool use — acceptable because the deterministic writers, not the model, own every file mutation.

The meta-lesson: "works in my terminal" and "works as a launchd daemon" are separated by the entire macOS security model.

## Iteration 4 — Audit-driven extraction: stop eyeballing (early June 2026)

**What broke.** An adversarial audit subagent was pointed at the extraction SOP and scored it **6/10**, with receipts: a teardown claimed an "orange accent" where the site's CSS variable was actually grey `#666`; EB Garamond was loaded but never mentioned; the tech stack was visible in script tags and discarded; no mobile pass existed. The model had been *eyeballing* screenshots and hallucinating plausible design tokens.

**What replaced it.** A mandatory DOM probe: one `browser_evaluate` call pulls CSS custom properties, `document.fonts`, sampled computed colors, meta/OG tags, element counts, headings, `scrollHeight`, framework globals, and script hosts. Plus fullPage screenshots, a text-first mobile resize pass (390×844), and an explicit anti-hallucination rule: colors and fonts MUST come from the DOM, never from looking at pixels. New structured fields landed: `tech_stack`, `palette_tokens` (each marked `var` or `rendered`), `fonts_loaded`, `meta`, `media_mix`, `page_height_px`, `headings`, `responsive_note`, `links_out`, `weight`. The [[mo1.app]] note shows the payoff — it correctly reports `--highlight-color: #fe9024`, `--accent: #666`, and that the site ships *no webfont at all*, the exact class of facts the old SOP got wrong.

This also established the project's working method: **audit → fix → re-verify**, with the audit run by an agent instructed to be adversarial rather than agreeable.

## Iteration 5 — Media understanding (June–July 2026)

**What broke.** Many bookmarked tweets showcase the cool thing in an image or video with *no link at all*. The pipeline was filing them as "uncategorized, link-free" — losing exactly the content they were bookmarked for.

**What we built.** Photos are downloaded and actually viewed by the model; videos are frame-sampled at 25/55/85% of duration via Chromium seek-and-screenshot — after discovering the hard way that Playwright's bundled ffmpeg cannot demux tweet mp4s. Each media item gets a stored description. Link provenance also got formalized: `resolved_links[]` records every URL with a `role` (primary / author-portfolio / related / reply-link) and `source` (tweet-body / reply / metadata).

**A deliberate dead end not taken:** logging into X from the automation browser would surface reply-only links, but risks the account. Decision: stay logged out and accept that reply links are best-effort. Another explicit human call.

## Iteration 6 — Scale and economics (June–July 2026)

**What we built.** The full backfill: the corpus went from **12 → 115 teardowns** across resumable chunked runs, surviving two rate-limit stops by design (the ledger only advances on success, so a killed run simply resumes).

**What broke along the way.**
- **The churn bug:** domains the enricher *declined* to tear down were never recorded, so every run re-queued them forever. Fixed with an attempted-set (`inspo/_backfill_attempted.json`, now 108 entries) — "we tried" is state worth persisting, distinct from "we succeeded".
- **The 53-bookmark near-miss:** a catch-up export almost went through as ONE giant `claude -p` call — one rate limit away from losing everything. `run.sh` was redesigned to loop in chunks: `ingest --limit 5` per enrich pass, apply, advance the ledger, repeat. A failed chunk costs one chunk.
- **Economics:** enrichment switched from Opus to Sonnet via `NEOUD_ENRICH_MODEL`. On subscription billing there's no per-token cost, but rate limits are real — and screenshots (images) turned out to be the dominant token cost, not text.

## Iteration 7 — The move, or: how we lost our own history (~2026-07-05)

The project was relocated out of its parent repo (neoud.net) into a standalone directory — and the `.git` stayed behind. All commit history from the first month is gone; `git log` here starts 2026-07-05 with a single squashed "Initial commit". The daemon also broke (its plist pointed at absolute paths in the old location) and the venv had to be recreated.

Lesson, and a real one: **absolute paths plus externally-registered daemons make a project move-hostile.** launchd doesn't know your repo moved; TCC grants don't follow; venvs embed their own path. The fix was mechanical (re-point the plist, rebuild the venv, fresh `git init`, private GitHub backup — 232 MB with screenshots), but the early history is unrecoverable, which is partly why this file exists.

## Iteration 8 — Vault v1: hub-and-spoke (July 2026)

**What we built.** The first knowledge-graph rendering of the corpus: one note per site plus *hub notes* per pattern, category, tech, color, font, and aesthetic, all joined by wikilinks, with an INDEX as the entry point. Inspired by Karpathy's llm-wiki (index → small linked pages) and PuppyGraph's knowledge-graph-agent (walk typed edges instead of scanning): an agent should read ~20 KB per lookup instead of grepping the 1.1 MB `inspiration.json`.

**What broke.** The first build exploded: **779 pattern hubs, 292 tech hubs, 203 font hubs** — the overwhelming majority linking exactly one site. A hub with one spoke is just a file. Share-thresholds (only create a hub if N+ sites share the value) cut it to ~210 notes, but the underlying problem remained: free-text keywords produce a graph of singletons.

## Iteration 9 — Vault v2: flat notes + free tags (July 2026)

**What we built.** Owner direction: "each node is a website; tags connect them." So: kill the hubs, one note per site carrying ALL its data, connected by nested tags (`#pattern/x`, `#tech/x`, `#font/x`, …). Committed as "Redesign vault: one flat note per website, connected by nested tags".

**What broke.** The Obsidian graph was a hairball: **1,277 tag nodes, 76% of them singletons** connecting nothing, at **~18.6 tags per note**. Same disease as v1 in different clothes — moving free-text vocabulary from hub notes into tags doesn't make it a controlled vocabulary. Also a comedy gotcha: Obsidian silently created a fresh empty vault in a subfolder, so the owner opened the graph and saw *nothing* — the first debugging session was against the wrong vault.

## Iteration 10 — Vault v3: controlled facets (July 2026, current)

**What we built.** Stepped back to first principles: what is the vault *for*? Answer: finding sites by **KIND** (vertical — what it is) and **FEEL** (vibe — how it reads), with **TOPIC** bridging clusters (a personal blog *about* startups links into the startup-product cluster) and **mode** (dark/light) as a cheap filter. `tools/ingest/taxonomy.json` became the contract — 11 verticals, 10 vibes, 18 topics, 3 modes, each value defined in prose so both the enricher and a backfill classifier apply them consistently.

The 155 existing sites were backfilled by a chunked, text-only `claude -p` classifier (no browser — it classifies from the already-extracted prose, 20 sites per call, resumable). New sites get facets from the enricher at ingest time.

**The numbers that justify three iterations:** **40 tag nodes (3 singletons)** versus v2's 1,277 (976 singletons); **919 site↔site edges**, each printed with its WHY in the note's Related-sites section ("shared: portfolio, minimal, dark"). The granular detail — keywords, tech, fonts — stays in the notes as searchable text and never becomes graph structure. The taxonomy is the graph; everything else is grep.

## Working methods worth naming

- **The audit → fix → re-verify loop.** An adversarial subagent scoring the SOP (Iteration 4) caught what self-review never would. This became the default way to harden any stage.
- **Deterministic/judgment split.** Everything idempotent, diffable, and file-mutating is plain Python with tests; the model only does what a script cannot (pick the subject site, write prose, classify). The seam between them is a JSON contract in `inspo/_inbox/`.
- **Explicit human decision points.** The prose schema pivot, staying logged out of X, Opus→Sonnet, keeping the backup private — none of these were model decisions, and recording them as decisions is part of the design record.
- **The `design-inspiration` skill.** A global skill in `~/.claude/skills` teaches any future agent how to traverse the vault (facet tags → notes → screenshots), so the corpus is consumable without knowing this project's internals.

## Iteration 11 — Visibility and self-documentation (2026-07-10)

**What we built.** Two operator-experience upgrades. First, the daemon now talks: `run.sh` posts macOS notifications (top-right, via `osascript`) when a run starts ("Started — N new bookmarks"), per chunk ("Parsing 5 websites… 10 done, 38 remaining"), on failure ("will resume next fire"), and on completion ("Done ✓ N processed — vault updated"). A background process that rewrites your data shouldn't be invisible. Second, the project became self-documenting: a global skill (`inspo-iterations-log`) plus a repo `CLAUDE.md` instruct any agent that changes the pipeline to append to this very file unprompted — the log stops depending on the owner remembering to ask.

**What broke or what we learned.** The first real-world test arrived immediately: a fresh bookmark export downloaded as a 2-byte file containing `[]` (X produced an empty export). `newest_export()` picked files purely by mtime, so the corrupt newest file would have shadowed the valid 4.4 MB export behind it — the daemon would have reported "nothing to do" forever.

**What replaced it and why.** `newest_export()` now walks candidates newest-first and returns the first that parses to a non-empty JSON list, logging `SKIPPING invalid/empty export` for the rest. A failed download can no longer wedge the pipeline; it degrades to the last good snapshot.

## Iteration 12 — Node 20, and a README for the front door (2026-07-10)

**What we built.** A proper `README.md` — what the system is, the pipeline diagram, how the repo is organized, how to browse the vault (Obsidian + ripgrep-by-facet), and the actual usage loop: bookmark on X → export with [twitter-web-exporter](https://github.com/prinsss/twitter-web-exporter) into `~/Downloads` → the daemon does the rest.

**What broke or what we learned.** Teardowns had started *silently skipping*: `@playwright/mcp` requires **Node ≥ 20**, and the daemon's PATH pinned nvm's v18.20.8. The MCP server printed a version error and exited, so the enricher simply had no browser tools — no crash, no error in the run log, just quietly thinner output. The failure mode rhymes with the cmux-wrapper and profile-lock incidents: every dependency the daemon reaches through (interpreter, claude binary, node, browser profile) fails *silently* in headless contexts.

**What replaced it and why.** `enrich.sh` and the plist now pin nvm's **v20.20.2** (overridable via `NEOUD_NODE_BIN`), with the requirement documented in both the script comment and the README's setup section.

## Iteration 13 — Beyond X: the universal URL adapter (2026-07-14)

**What we built.** The ingestion opened up to any medium. The realization: the pipeline's real seam is `new-items.json` — everything downstream (enrichment, teardown, facet classification, vault) doesn't care where an item came from. So `tools/ingest/add_urls.py` became the universal adapter: give it URLs (CLI args or a file of one-per-line), it builds normalized items with `source: "manual-url"`, dedupes by URL-hash against the ledger and by domain against existing teardowns, and drives the same chunked enrich→apply→render chain. The daemon grew a second watched medium: drop `inspo-urls*.txt` in `~/Downloads` and it ingests the list and archives the file. Browser bookmark exports, Raindrop/Pocket CSVs, pasted links — all reduce to a URL list, so all now feed the vault.

**What broke or what we learned.** Nothing broke — this one was pure leverage from earlier decisions. Because the deterministic/judgment split already isolated "where items come from" (deterministic) from "what to do with them" (model), a new medium cost ~130 lines and one prompt rule (`manual-url` items skip the tweet/media steps; the submitted URL is always torn down, and a deep link is torn down as that page, not its homepage).

**What replaced it and why.** Nothing replaced — added. First site through the new path: [[vivekhaldar.com]] (`/ideaverse/chord.html`), submitted as a bare URL in chat.

## Iteration 14 — Naming the input bottleneck (2026-08-17)

**What we built.** Not code — a thinking document, `docs/autonomous-growth.md`. A real lookup ("artistic references for a DJ site") surfaced the structural limit: the pipeline is fully automatic *downstream* of a manual act, so the corpus is a sample of my X attention rather than of good web design. The bias is measurable in `INDEX.md` — 84 `#vibe/minimal` vs 3 `#vibe/brutalist`, `#topic/design`/`ai`/`engineering` at 55/44/41 vs `#topic/fashion` and `#topic/photography` at 1 each, and no music/nightlife cluster at all. The doc separates two ambitions that had been blurred together: (A) autonomous discovery so the corpus finds its own inputs, and (B) a public open-source search engine over design characteristics. It also restates the v1 design and the five load-bearing invariants (deterministic/judgment split · anti-hallucination extraction · chunked+resumable with ledger-last · one source of truth · controlled facet vocabulary) so any future version has something to be measured against.

**What broke or what we learned.** Two things worth writing down. First, Iteration 13's universal URL adapter turns out to be the enabling decision for autonomy: discovery is a new *producer* in front of an existing socket, so Ambition A needs no change to the ingest core. Second, the hard problem isn't discovery (cheap, easy) — it's the quality gate, because choosing to bookmark is taste I currently supply for free. Sketched as a cascade: mechanical prefilter (curl+grep for parked/template/no-custom-CSS) → screenshot-only triage → full teardown → post-hoc pruning of sites nothing ever links to. Noted explicitly that judging-from-pixels is permissible for *routing* but stays forbidden for *data* (invariant #2 holds). Best idea to come out of it: **gap-driven discovery** — read the taxonomy's thin facets and crawl for those specifically, so the taxonomy becomes the crawl planner and volume (hence cost) stays low.

**What replaced it and why.** Nothing replaced; nothing built. Deliberately kept to ideas — no schema, taxonomy, daemon, or hosting decisions. The doc names one cheap next test (gap-driven discovery against a single thin facet, ~20 candidates, existing pipeline, judged by whether a real lookup improves) so the first move doesn't require committing to the architecture.

## Iteration 15 — The in-repo queue: a producer that isn't on this Mac (2026-10-17)

**What we built.** A third ingest medium, so an agent with no access to this machine can feed the pipeline. The question that started it was "can Obsidian read from Notion?" — it can't, only one-shot imports exist, and it was the wrong question anyway: `inspo/vault/` is a *generated view*, so anything writing into it gets flattened on the next rebuild. The right shape was to put the remote agent at the *front* of the pipeline, as another producer in front of Iteration 13's URL socket — exactly the move Iteration 14 predicted autonomy would need. Three pieces: `inspo/_queue/*.txt` (a tracked inbox, same one-URL-per-line-with-`#`-comments format as the `~/Downloads/inspo-urls*.txt` drop-files, so there is no second format to keep in step); `tools/ingest/drain_queue.py`, which hands each queued file to `add_urls` and `git rm`s only the ones that land; and `tools/ingest/sync_repo.py`, which gets the daemon talking to `origin` at all — before this, `run.sh` and `tools/` contained **zero** git commands, so a PR merged on GitHub was invisible locally. Plus `StartInterval` 1800s in the plist, because `WatchPaths` on `~/Downloads` cannot see a merge. 29 new tests (27 → 56), the sync ones against real throwaway git repos since the whole point is how git behaves on a dirty tree.

**What broke or what we learned.** Four things, one of them a wrong premise I'd already written down as the plan. (1) **"Commit then `merge --ff-only`" cannot work.** The daemon's tree is dirty after every run by design — 100 generated paths dirty at the time of writing — so the plan was to commit that output first, then fast-forward. But committing locally is *what makes the branches diverge*: once HEAD has a local commit and origin has the merged PR, local is no longer an ancestor of remote and a fast-forward is impossible by construction. Caught by a test asserting `FF_OK` that returned `FF_DIVERGED`. Replaced with four explicit cases (`FF_UP_TO_DATE` · `LOCAL_AHEAD` · `FF_OK` · `MERGE_OK`, conflict → `merge --abort` + `MERGE_CONFLICT`), which is safe here only because the two sides write disjoint paths: the remote only ever adds `_queue/` files, the daemon only ever writes generated output. (2) **`git add -- inspo/ screenshots/` fails as a whole if either directory is missing**, silently staging nothing and reporting a clean tree — a test on a fixture repo without `screenshots/` found it; now it stages the detected paths, not the prefixes. (3) **`git rm` fails on an untracked file.** A queue file arriving by PR is tracked, but one dropped in by hand isn't, so the drain reported success and left the file in place — it would have re-ingested on every fire forever. Found by a smoke test against the live repo, not by a unit test; fixed with an unlink fallback. (4) A plist discovery, and then a **retraction of my own conclusion from it**. `~/Library/LaunchAgents/` does hold a stale *copy* rather than a symlink — the installed job was pinned to Node `v18.20.8` while the repo copy had said `v20.20.2` since Iteration 12 — and I wrote that up as "the Node 20 fix never ran, teardowns have been degrading since July." That was wrong, and reading `enrich.sh` two minutes later showed why: lines 16-17 prepend `$HOME/.nvm/versions/node/v20.20.2/bin` to `PATH` *themselves*, and that line is part of the same Iteration 12 commit, in a tracked file the daemon executes from the repo. The plist's Node entry is a redundant belt to `enrich.sh`'s braces. Measuring it made the point twice over: under the old plist `PATH`, `node` resolved to `/Users/neoudhaile/.local/bin/node` = **v26.9.0**, because `.local/bin` precedes the nvm directory — so the plist's nvm pin was never what supplied node at all. `npx @playwright/mcp@latest --version` then printed `0.0.83` cleanly under the daemon's exact environment. The plist drift is real and worth fixing; the degradation I inferred from it never happened. Iteration 14's original explanation (the failing run had already spawned before the fix landed) stands.

**What the first live fire taught.** Worth separating from the above, because it was caught by running the thing rather than by testing it. Two fires went off (removing the trigger file is itself a `~/Downloads` change, so `WatchPaths` fired twice). Fire one drained the queue correctly end to end — `SYNC COMMITTED 1 LOCAL_AHEAD` · `QUEUE_DONE 1 file(s) 1 url(s) 0 failed` · `PUBLISH COMMITTED 2 PUSH_OK`. Fire two exposed a hole: it committed a leftover archive file during its **pull** phase, then hit `nothing to do` — and that early exit sits *after* the sync but *before* the publish step, so the commit was stranded unpushed. Local was left ahead of `origin/main`, which is precisely the diverged state pushing exists to prevent; the next merged PR would have forced a merge commit instead of a clean fast-forward. `do_pull` now pushes whenever it leaves local ahead, so "committing implies publishing" holds at both ends of the run. The same fire also showed `COMMITTED 2` against a commit containing one file: the status counted paths *detected dirty* rather than paths *staged*, and a status line that disagrees with its own commit is worse than none, so it now counts what actually landed. 60 tests.

**What replaced it and why.** Push is now part of the design rather than the nicety Open threads called it: an unpushed daemon commit plus a new PR on origin is a diverged main, so *not* pushing breaks the next sync. The daemon therefore commits and pushes its own output every run. The guard that makes unattended committing tolerable is ownership by path prefix — `inspo/` and `screenshots/` are the daemon's, everything else is the human's, and if **any** foreign path is dirty the daemon commits nothing and skips the merge entirely. That keeps a work-in-progress edit to `run.sh` from being swept into a daemon commit or clobbered by a merge landing on top of it; the cost is that the queue stalls while the repo has uncommitted hand edits, which is the right trade for an unattended process. Sync is also never fatal (`main()` always exits 0) and runs under the existing `mkdir` lock, so a bad sync degrades to "work on local items only" and never advances the ledger.

## Iteration 16 — The queue medium, run for real (2026-10-17)

**What we built.** Nothing new; Iteration 15's queue was exercised end to end by an actual agent, which is the only test that counted. Muse watched 44 saved Instagram reels, picked out 17 sites it judged teardown-worthy, annotated each with what the *video* showed, and opened PR #1 — it has no access to this Mac, which is the whole reason the medium exists. On merge the daemon's sync took the diverged path exactly as designed (`SYNC COMMITTED 2 MERGE_OK PUSH_OK`: local generated output committed, the PR commit merged on top, pushed), the queue file arrived with all 17 URLs, dedup dropped `21st.dev` as already torn down, and the remaining 16 went through enrichment in four chunks. Result: **304 → 320 items, 186 → 201 site teardowns, 174 → 189 screenshots**, vault rebuilt to 203 notes. The producer knew nothing about teardowns, screenshots or taxonomy, and nothing in the ingest core changed to accept it — which is what Iteration 13 bought and Iteration 14 predicted would matter.

**What broke or what we learned.** Three things, and the first is the worst bug this project has had. (1) **A run that rebuilt 93 paths committed one file and called it success.** `PUBLISH COMMITTED 1` on a run that had just written 15 teardowns, 15 screenshots and a full vault. The cause is a collaboration between two correct-looking pieces: `drain_queue`'s `git rm` stages its deletion the moment a queue file lands, so the index is already non-empty when publish runs; when the subsequent `git add` of the run's output failed, `commit_generated` fell straight through to the commit, found that one staged deletion, counted it honestly, and reported a successful publish while the real output stayed dirty and unpushed. Two commits earlier I had "fixed" exactly this shape of bug by counting staged paths rather than dirty ones — the count was honest, the decision to commit at all was not. The likely trigger is `index.lock` contention, since this checkout is now shared by a 30-minute daemon and two parallel sessions. (2) **The agent medium has no way to tell a live site from a parked domain.** `terminalindustries.com` came in as the batch's strongest recommendation — "the entire video is a design breakdown of this site" — and resolved to a GoDaddy for-sale stub returning 403. Enrichment handled it correctly (no screenshot, no probe, no facets, item kept with `todo-find-url`), but a producer that cannot fetch cannot validate, so every agent-sourced URL is a claim rather than a fact. (3) **The SOP is being skipped consistently, not randomly.** All four chunks independently skipped the hover/scroll interaction step and left `weight.requests` null, and each one said so plainly in its summary. That is a prompt problem, not a model failure — optional-sounding steps at the end of a long SOP get dropped under token pressure every time.

**What replaced it and why.** A non-zero `git add` now returns `ADD_FAILED` and nothing is committed or pushed on either the pull or the publish side, with a notification; `index.lock` specifically is retried once first, since contention is not an error. The run's output simply stays dirty and the next fire takes it intact — which is the same ledger-last discipline the enrichment chunks already follow, applied to git. Publishing the stranded 93 paths through the fixed path returned `PUBLISH COMMITTED 93 PUSH_OK`. Also collapsed two ahead-of-origin helpers that the two parallel sessions had each grown independently, keeping the stricter one: a *diverged* local is not "ahead", because pushing it would be rejected. 66 tests.

## Iteration 17 — Checking the claim before paying for it (2026-10-17)

**What we built.** `tools/ingest/urlcheck.py`, a mechanical prefilter that runs at drain time: every queued URL is fetched, redirects followed, and dead or parked domains dropped before `claude -p` is invoked. Wired into `drain_queue`, which now hands the runner a filtered copy and writes the rejects to `inspo/_archive/<stamp>-<name>.rejected.txt` **with their reasons and the agent's own notes attached**, so a wrong call is auditable and a domain that comes back to life can be re-queued. Redirects are resolved and rewritten to the final address, which also fixes something Iteration 16's run surfaced by hand: `cavalry.studio` → `/en/` and `palmier.io` → `www.`, both of which the enricher had to notice and reconcile itself. 20 new tests (66 → 86), all offline.

**What broke or what we learned.** The design assumption in the open thread was wrong, and measuring it first is the only reason the module works. I had written that a prefilter should "reject parked/4xx/5xx" — but probing the actual failure before writing any code showed `terminalindustries.com` answering **HTTP 200**, with this entire body: `<!DOCTYPE html><html><head><script>window.onload=function(){window.location.href="/lander"}</script></head></html>`. 114 bytes, no title, no stylesheet, a JS bounce to a GoDaddy lander. A status-code filter — exactly what was specified — would have passed it straight through to enrichment. The test had to be *does this page have any content*, not *was the server polite*. Two smaller things: `<title>  </title>` read as a real title because the regex asked only whether a non-space character followed the tag, and the `<` of the closing tag satisfies that; and the first version wrote rejects using the module-level `ARCHIVE`/`INBOX` constants, so draining a queue in any other directory would have written into this repo — both caught by tests rather than by running it.

**What replaced it and why.** The filter is deliberately one-directional: **reject only on clear evidence, let doubt through.** A `401/403/406/429` is explicitly *not* a rejection, because real sites bot-block a bare `urllib` request and open fine in the browser Playwright drives — dropping a site somebody watched a video to find is irreversible and expensive, while letting a bad one through costs one chunk and an item enrichment already handles correctly. Parking markers are matched only against small bodies, so a real page containing the words "for sale" is never caught. Verified against the live batch: the parked domain and a nonexistent domain rejected, `gsap.com`, `lenis.dev`, `cavalry.studio` and `palmier.io` all passed with their redirects resolved. `NEOUD_SKIP_URLCHECK=1` bypasses the whole thing for offline runs, and the test suite uses it so nothing in CI touches the network.

## Iteration 18 — Measuring the corpus found the bug in the thing that measures it (2026-10-17)

**What we built.** Nothing — this is a bug fix to Iteration 17, found an hour after shipping it, by pointing the new prefilter at the 201 existing teardowns to answer "how many have gone dead?". The sweep reported 13 dead. One of them was `claude.com`, which is self-evidently not dead, and that one obviously-wrong row is the only reason the rest got examined.

**What broke or what we learned.** Two bugs, both of which would have silently dropped real sites out of the queue — the exact failure Iteration 17's docstring calls the expensive, irreversible one. (1) **Python 3.9's `urllib` follows 301/302/303/307 and stops.** It does not follow **308**. A site on a permanent 308 returns its own 15-byte `Redirecting...` body, which has no title and no stylesheet, so the stub rule classified it as a parking page. `gregisenberg.com` and `killedbyopenai.com` are real sites that were rejected for using a standard redirect. Verified directly: `hasattr(HTTPRedirectHandler, "http_error_308")` is `False` on this interpreter. (2) **An empty body was treated as evidence.** Under 12 concurrent workers with a 10-second timeout, `claude.com`, `silk.art` and `gregisenberg.com` returned 0 bytes; fetched alone, every one returns 65536. A truncated read tells you nothing about the site, but `looks_like_stub("")` is trivially true — small, titleless, unstyled — so the filter read its own timeouts as dead domains. The deeper lesson is that the check had a failure mode that *scales with load*, so it would have gotten worse exactly when a big batch arrived.

**What replaced it and why.** A `_Follow308` redirect handler, and an explicit rule that an empty or whitespace-only body returns **allowed** with the reason "nothing learned" rather than falling through to the stub test — consistent with the module's stated one-directional bias, which the stub rule had been quietly violating. A read that fails mid-body now reports an error instead of returning an empty string, so the two cases stay distinguishable. Re-running the sweep at 6 workers and a 20-second timeout: **5 dead of 201**, not 13. The survivors are `arneshbanerjee.github.io`, `axiaisacat.indiehacker.bio` and `hofai.io` (404), `ciggies.app` (DNS), and `pradamodenewyork.eventbloomer.com` (502, possibly transient). 90 tests. The sweep itself is still a one-off script and not a pipeline stage; the open thread below stands.

## Iteration 19 — Asking what a site IS: embeddings, discovered clusters, and the essence (2026-10-19)

**What we built.** Three things, in the order the data forced them. (1) **Embedding-based clustering** (`tools/ingest/embed.py`, `cluster.py`) to replace the four controlled facets as the way sites relate. The owner brought four searches the vault could not answer — "personal websites" (split across `portfolio` and `personal-blog`), "sites that use books as a motif" (no field, though `book` appears in 68 of 201 teardowns' prose), "good light minimalist design" (`vibe/minimal` was on 99 of 201 sites, so it narrowed nothing), and "visualise the clusters" (only reachable through an agent). And `pattern_keywords`, the one extensible field, had collapsed into 930 terms of which 746 were used exactly once. Each teardown is now embedded twice — a **purpose** space and a **design** space — with Gemini `gemini-embedding-001` (1536-d, cached by exact text), then clustered with a Ward dendrogram, cut at any depth, with symmetrized k-nearest-neighbour edges. (2) **Versioned cluster vaults** (`tools/ingest/render_clusters.py`): every reclustering renders `inspo/cluster-<n>/purpose/` and `/design/` as separate Obsidian vaults whose only notes are websites, so no theme can become a node; cluster membership is a hidden frontmatter tag used purely for colour. (3) **The essence** (`tools/ingest/essence.py`, enrich step 7e): six fields — `subject, host, does, for_whom, domain, kind` — now asked of the agent that has the live site, validated by one shared checker, backfilled for the whole corpus.

**What broke or what we learned.** A lot, mostly from looking at real output rather than tests. *Clustering:* average linkage put **183 of 201 sites in one cluster**; Ward gave 44/40/38/24/19/17/8/7. Ten sites formed a cluster named "extracted captured. screenshot" because their teardowns had *failed* and they shared the placeholder text — the prose narrates the pipeline (WebFetch fallbacks, bot walls), so it is now scrubbed sentence by sentence. Cluster names were full of `scrollheight` and `static.cloudflareinsights.com`. On the design space the result was immediately good: `minimal`'s 99-site blob became 8 looks and 22 sub-looks, and it found an aesthetic no taxonomy would have — the deliberately-plain, browser-default-blue personal site (daryl.cv, farza.com, mrdoob.com) as its own cluster. *The owner's review of the purpose space* found it vague, with three concrete misses: fabra.com never surfaced as fashion, appdrop.com was called a "personal maker app", and appdrop and comnyang (a desktop pet cat) sat in one cluster. The cause was the text recipe — `what_it_shows` and `how_it_works` describe the *page* and were ~80% of each embedding; fabra's "3D apparel design platform" was 17% of its own vector, and appdrop and comnyang were grouped on shared Next.js-and-analytics vocabulary. Embedding `what_it_is` alone split them, but fabra still clustered by *kind* (generative tools) over *domain* (fashion): one vector cannot keep two independent axes apart. *The root cause was upstream.* `enrich_prompt.md` is exhaustive about capture and never asked for meaning — the four prose fields were undefined, and rule 7e told agents to "name the real framework" in prose. Agents were precise about pixels and improvised about purpose. And appdrop was not an embedding failure at all: its stored URL is `appdrop.com/marcgmbh/link-bouquet`, one user's mini-app, so the teardown faithfully described the wrong subject — 24 of 201 entries store a deep page, and 19 more have `what_it_is` opening "the landing page for…". A three-site test of a scrape-time essence prompt on headless Sonnet 5.5 got all three right (fabra: domain "fashion and apparel"; appdrop: subject Link Bouquet, host AppDrop the creator-app platform; comnyang: "desktop pet app"), and taught three more things: one of three answers was malformed JSON (a stray quote), one session **read its working directory** and reported on sites it was never asked about, and one turned a page-title fragment ("· Danger Testing") into a platform identity. *The live re-scrape of the 42 problem sites* (all 42 ok, $5.38) then hit link rot: three sites had died or shut down since capture — Arnesh Banerjee's research homepage now 404s, Fey was acquired and is a sunset notice, the Prada Mode event page 502s — and the first run **replaced their good original prose with descriptions of the error pages**. That was a design error, not a model one: a live run treated the site as it is *now* as the truth, but this library records what the owner *saw*.

**What replaced it and why.** The essence is now the meaning layer, produced at the one stage that has the source: step 7e of the SOP, written before any prose, with `domain` and `kind` deliberately separate fields, rule 0 opening the domain root as well as a sub-page, one-line contracts for each prose field, and **tech confined to the `tech_stack` sidecar**. One validator serves every producer and `apply_enriched` — page-shaped kinds ("landing page", "marketing site") are rejected, and an invalid essence is dropped and marked rather than failing an unattended run. `loads_loose` repairs the JSON slips actually seen. Every headless run gets its own empty temp directory. Live results now carry a required **`site_state` (`live` / `gone` / `sunset`)**, and only `live` may replace prose; a dead or sunset site keeps its original capture, gets the state recorded beside it, and takes its essence from that capture — verified by re-running the three (gone, sunset, gone; prose intact) and a healthy control (fabra: `live`). Problem-site selection skips sites a live run already settled, so a cleared cache cannot cost a re-scrape. The other **162** sites were backfilled from stored prose in batches of 8 ($2.46). **Every one of 201 sites now has an essence: 39 live, 162 from prose; confidence 155 high, 40 medium, 5 low** — the five lows are exactly the sites whose original teardown failed. Total spend ~$8.31. Embeddings stay on Gemini (free tier, needed pacing for per-minute 429s); everything that reads or writes meaning stays on Sonnet, per the standing rule.

## Iteration 20 — Naming the clusters, and letting the names do the reviewing (2026-10-20)

**What we built.** Human titles for every cluster (`tools/ingest/cluster_titles.py`), written by Sonnet from what the members actually are: purpose clusters from their members' essences, design clusters from their design prose. The renderer carries each title as a **named, nested tag**, so a family is `#designer-and-studio-portfolios` and a sub-cluster `#designer-and-studio-portfolios/design-studios-and-agencies`. `render_clusters --relabel cluster-<n>` names an existing version in place, and every new version gets titles by default, recorded in a `titles.json` beside it.

**What broke or what we learned.** Three things. (1) **Obsidian's graph colour groups have no label field.** The group shows its search query and nothing else, so `#cluster/3` was the only name the owner could see. The name had to live in the tag itself: the query `tag:#designer-and-studio-portfolios` *is* the label. Nesting makes one group colour a whole family, because `tag:#parent` also matches `#parent/child`. (2) **The version on screen could not be re-rendered from its own data.** `inspo/_clusters/purpose.json` had been overwritten by a later run, so re-rendering `cluster-1` from it would have silently swapped in a different clustering under the same name. The relabel instead rebuilds the result from the vault's own notes (paths from frontmatter, edges from each note's "Nearest" list, settings from the README) and checks that membership is unchanged. (3) **The owner had tuned the graph by hand** (repel 14.8, centre 0, zoom 0.31), and a re-render would have reset that. The renderer now merges into an existing `graph.json` and replaces only `colorGroups`.

**What replaced it and why.** The prompt requires honesty: a cluster whose members share no clear theme is titled "Mixed: a, b, c". That turned the names into a review instrument, and they reached the same verdict as the by-hand review of `cluster-1` from Iteration 19 without seeing it. **Purpose: 5 of 30 clusters are "Mixed"**, including 3 of the 8 families. These are the companies grouped by their pitch ("Mixed: AI and developer SaaS products"), the indie apps and directories, and the ambient and thin-data residue. These are exactly the clusters the manual read flagged. The coherent ones get the names you'd give them: "Designer and studio portfolios", "Founder and engineer personal sites", "Open-source animation and UI libraries", "Infinite zoom artworks". **Design: 2 of 30 are "Mixed" and every family is coherent**: "Warm paper and cream craft", "Dark neon and terminal", "Retro pixel desktop nostalgia", "Default-styled researcher homepages". That's confirmation, from a second angle, that the design space already works and the purpose space needs the essence. The "Mixed" count is now in each version's README, so `cluster-2` can be judged against `cluster-1` on a number as well as a read.

## Iteration 21 — Colour by family, and a hub nobody asked for (2026-10-20)

**What we built.** One colour group per *named* cluster (22 per space instead of 8), **coordinated by family**: hue encodes the family, so the graph reads as eight colour regions, and shade separates the siblings inside it. A "Mixed:" cluster keeps its family's hue but drops to near-grey saturation, so the clusters the titler could not name show up as washed-out patches. `INDEX.md` became a colour legend: every cluster name has a swatch in its exact graph colour.

**What broke or what we learned.** (1) **The owner tried to name the groups by hand, and nothing coloured.** He replaced the `tag:#…` queries with typed names. A graph group is a search query, so a bare name is a full-text match on its words, not a cluster lookup. Obsidian also writes its in-memory graph settings back to `graph.json` while the vault is open, which can silently undo a render. (2) **Nested tags were unreadable in the one place names appear.** The group panel truncates queries at about 20 characters, so both children of `designer-and-studio-portfolios` showed as the same `tag:#designer-and-studio-…`. Tags are now flat and unique across the space: each note carries its family's tag and its cluster's tag, so the panel shows the cluster's own name. (3) **`INDEX.md` had been a hub since `cluster-1` was first rendered.** It wikilinked all 201 sites, so the largest node in every graph was the index, pulling everything towards the centre. That broke "every node is a website" and had been distorting the layout all along, including the layout the owner judged the clustering by. It now lists sites as plain text. (4) **Lightness alone does not separate siblings.** Six shades of one yellow read as one colour, so the hue now also fans ±0.04 inside each family. The tests then failed on the red family, because its fan wraps the colour wheel from 0.96 to 0.04, which is 0.08 apart around the wheel and 0.92 in a straight line. The tests now measure hue distance around the wheel.

**Follow-up, same day:** the `tag:#…` groups loaded but coloured nothing, while the owner's hand-typed names did. The tags were valid, so the likely cause is Obsidian's tag index lagging behind three rewrites of an open vault's tags. A phrase search reads the file itself. Groups now match each cluster by its **exact name as a quoted phrase** (quoted, because an unquoted name ANDs its words across the whole note and `Mixed:` reads as a search operator). The name is also what the panel shows, and a check confirmed all 44 phrases match exactly their own cluster's notes.

**What replaced it and why.** Groups at the second level, ordered family by family, so the panel itself reads in colour blocks. The renderer still merges into an existing `graph.json` and replaces only `colorGroups`, so the owner's hand-tuned forces and zoom survive every re-render. 186 tests.

## Iteration 22 — Edges that keep colours together; screenshots that actually load (2026-10-20)

**What we built.** Graph edges built from the cluster structure (`cluster.structured_edges`). Each site links to its 4 nearest sites *inside its own cluster*, plus 1 in a sibling cluster of the same family, and none across families. These are the "separate but close" mechanics from the October design, finally wired in. A site's overall nearest neighbours in other clusters stay in its note as plain text ("Also close, in other clusters"), so they're still readable but no longer pull on the layout. Screenshots are symlinked into each vault as `_screenshots/`.

**What broke or what we learned.** Once colouring worked, two things were visible. (1) **The colours were scattered across the graph, not clustered.** Plain kNN put only **45% of purpose edges and 38% of design edges inside their own cluster**, so most of the force layout's pull was across clusters. The clustering was fine; the edges disagreed with it. (2) **Screenshot PNGs showed up as graph nodes.** The notes embedded `../../../screenshots/x.png`, a path outside the vault that Obsidian cannot resolve. So the images had **never rendered in any cluster-vault note**, and each one was an unresolved link, which appeared as a node once the owner's graph reset "Existing files only".

**What replaced it and why.** After the change, **76% of purpose edges and 75% of design edges stay inside their own cluster, and 100% stay inside their family**, with no site left without an edge. **Bridges, added back the same day.** Cutting every cross-family edge also hid real relationships. Measured, **113 cross-family pairs per space are at least as similar as the median in-cluster edge** (0.814 purpose, 0.891 design), and the strongest are unambiguous: the same person's portfolio and gallery (daryl.cv ↔ recent.design), a course and its author's site (animations.dev ↔ emilkowal.ski), Joonas's portfolio and his Rothko piece. `bridge_edges()` gives each site at most one link, to its closest site in another family, only above that bar, listed in the note under "Bridges to other families". That adds back about one edge in seven, so families stay visibly apart but connected. Edges come from the current embeddings (cached; 39 purpose re-embeds for the sites whose prose was re-scraped) but never change membership, which stays as each version recorded it. 193 tests.

## Iteration 23 — Out of Obsidian: a hosted graph, and a public repo (2026-10-23)

**What we built.** A web graph that reads straight from GitHub. `tools/ingest/export_graph.py` writes `inspo/graph.json`. It clusters every site fresh, so new ones are included without waiting for a vault version. It covers both clusterings and types each edge `cluster`, `sibling` or `bridge`. Group titles are cached by the exact set of member sites, so a run that leaves membership unchanged never pays to re-title. `site/` is plain HTML and JS (`force-graph`, no build step) and does the following:
- groups sites into category clusters, with bridges between them
- zooms and pans
- opens a site's summary when you click it
- highlights a group's sites when you hover it in the legend
- switches between the purpose and design views
- searches for a site

The page loads `graph.json` from `raw.githubusercontent.com`, so it can be hosted anywhere. A Pages workflow deploys only when `site/` changes, and a daemon push of fresh data goes live without a redeploy. The daemon runs the export after every vault rebuild. The repo was made **public** at the owner's request so agents anywhere can read it without a login, after a scan of the full history found no secrets.

**What broke or what we learned.** (1) **The Obsidian plugin route stalled on tooling, not on the code.** The plugin was written, but the CLI loop needed to reload it and take screenshots stayed off despite the toggle. The owner chose to build our own UI instead. (2) **The headless `claude` login had expired**, with "OAuth session expired and could not be refreshed". Every daemon fire had been failing to enrich the same 1-item chunk. By design the ledger didn't advance, so nothing was lost, but nothing new got in. Titling now degrades to keyword names instead of crashing, and fallback names are never cached. A long-lived token from `claude setup-token` is the durable fix. (3) **The data file's location decides whether the daemon keeps working.** The daemon owns only `inspo/` and `screenshots/`, so `site/graph.json` would have looked like a hand edit and stalled every sync. The file lives at `inspo/graph.json`. (4) **`force-graph` empties the element it's mounted on**, which wiped the toolbar on the first test. It now mounts on its own `#canvas`. (5) Every headless call waited 3 seconds for stdin. `run_claude` now passes `DEVNULL`.

**What replaced it and why.** Obsidian stays a place to read notes. The graph you look at is now a hosted page over the same single source of truth. The remaining gap for agents is querying the data rather than parsing it: a small MCP server over `graph.json` and the embeddings is the next step.

## Open threads

- **The daemon's `claude` login expires:** an OAuth session lapsed and enrichment failed silently for days. Run `claude setup-token` for a long-lived token, and alert when `enrich failed` repeats.
- **Agents parse files; they can't query yet:** an MCP server over `graph.json` and the embeddings (e.g. similar sites, a group's members, search by domain) is the step that makes the public repo useful to agents beyond reading files.
- **Obsidian can overwrite a render while it is open:** it writes its in-memory graph settings to `graph.json`, so a re-render applied while the vault is open is lost on the next zoom or settings change. Today the fix is "reload without saving" after every render. A render could detect an open vault (`obsidian.json` marks it `open`) and warn.
- **The essence is not yet what the purpose space clusters on:** every site has one, but `embed.py` still embeds `what_it_is`. Deliberate (free embeddings, Sonnet per the standing rule), but it is a second key, a second rate limit, and a model that can be retired under us — `gemini-2.5-flash` already 404'd as "no longer available to new users" mid-session.

- **Concurrency is a correctness input to the checker, not just a speed knob:** the false positives only appeared at 12 workers / 10s. Anything added to this filter needs testing under load, not just alone.
- **The enrichment SOP is being skipped at the tail, every time:** all four chunks of the first real run independently skipped the hover/scroll interaction step and left `weight.requests` null. Consistency across independent calls makes this a prompt-ordering problem rather than a model one; the optional-sounding steps live at the end of a long SOP. Either promote them or drop them honestly from the schema.
- **One checkout, three writers:** a 30-minute daemon and parallel sessions now share this working tree, which is what produced the `index.lock` partial commit. `ADD_FAILED` makes that safe rather than silent, but nothing coordinates the writers; worktrees or a git-level lock are the real answer.
- **The foreign-path guard can stall the queue silently:** while any file outside `inspo/`/`screenshots/` is dirty — which is true the whole time I'm working in the repo — the daemon commits nothing, skips the merge, and so never sees queued work. It notifies, but a 30-min poll that keeps declining to sync is easy to miss. Needs either a staleness alarm or a narrower guard.
